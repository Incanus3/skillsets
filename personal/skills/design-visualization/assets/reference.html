Catalog snapshot publication

A publisher prepares a read-only catalog snapshot and switches a single active reference after validation. Review the change in reader-visible state and the recovery boundary.

Decision status: Ownership is an assumed constraint; reference switching is proposed. This worked example explains a fictional contract and supplies no implementation evidence or authorization.
01 / Ownership

Source records and published snapshots

Editors change source records. The publisher produces derived snapshots and owns the active reference; readers consume only that reference.

Assumption

Editor-owned source records

records/items.json

Read a fixed source revision. Publication does not rewrite records or mark them approved.

Proposed ownership

Publisher-owned snapshot and reference

snapshots/revision-42.json active.json → revision-41

Create a new immutable snapshot. Update the active reference only after validation and a fresh comparison with the expected revision.

Reader boundary: A prepared snapshot is not active. Readers continue using revision 41 until the reference switch succeeds.
02 / Operation flow

Validation, reference switching and reader verification

This sequence assumes one compare-and-swap operation for the active reference. Every edge states its condition; failure paths preserve the distinction between prepared, active and verified.

  1. 1

    Prepare the candidate snapshot

    Read source revision 42, generate the snapshot and validate required fields and unique item identifiers.

    Prepared revision 42
    Active revision 41

  2. Failure → stop: invalid fields or duplicate identifiers leave the active reference at revision 41. Retain the validation report.

    Valid candidate → step 2: compare the active revision before switching.

  3. 2

    Switch the active reference conditionally

    Replace revision 41 with revision 42 only if the current reference still equals revision 41.

    Before switch revision 41 expected
    After acknowledgement revision 42 active

  4. Conflict → re-review: a different active revision prevents the switch; inspect the competing publication before another attempt.

    Lost reply → inspect: read the reference before retrying. A missing acknowledgement does not prove that the switch failed.

  5. Switch acknowledged → step 3: verify the exact revision through the reader path.
  6. 3

    Verify the reader-visible snapshot

    Fetch through the catalog reader and compare the returned revision and snapshot digest with revision 42.

    Active revision 42 acknowledged
    Completion requires matching reader evidence

  7. Reader mismatch → report incomplete: preserve the active revision and mismatch evidence. Do not silently restore an older reference over another publisher's work.

  8. Matching revision and digest → complete: record the verified publication result.

Prepared; publication pending

Outcome: pending. The candidate passed validation, but a conflict prevented activation. No completed publication is recorded.

Active and verified

Outcome: complete. The switch was acknowledged and the reader returned the expected revision and digest.

03 / Decision comparison

Reference switching compared with in-place updates

The proposal separates preparation from activation. The comparison below uses the same criteria for both approaches.

Publication approaches: reader consistency, storage and recovery
ApproachBenefitCost and recovery limit
Proposed
Immutable snapshot + reference switch		Readers receive a complete revision. A conflicting publisher can be detected before activation.Retains snapshots and requires atomic compare-and-swap support. Lost replies require reference inspection; reader verification can still fail after activation.
Rejected in this example
Update the active file in place		Uses one file and avoids retained revisions.Readers can encounter partial content unless the store provides atomic replacement. Recovery needs a separately preserved version and fresh ownership checks.
Review decision: Accept the storage cost only if complete-revision reads and conflict detection are required. A system with atomic file replacement may justify a simpler contract.
Source / fictional contract

Example assumptions and unverified behavior

This embedded contract is the source for this worked example. It describes an invented catalog publisher; it is not a production specification.

Assumed operation and completion rule

The publisher reads a fixed source revision, validates a newly prepared snapshot, conditionally switches one reference and verifies the revision and digest through a reader. Validation failure or a reference conflict prevents activation. A lost switch reply leaves activation unknown until reference inspection. A reader mismatch leaves publication incomplete even if activation was acknowledged.

  • source revision
  • validation report
  • switch acknowledgement
  • reader revision + digest
